## 1. 项目概述

### 1.1 项目背景

本项目计划从零编写一个**实时操作系统（RTOS）** —— 命名为 **CatOS**，并在此基础上构建**复古游戏平台软件 CatGamer**，用于移植并运行 FC（红白机 / NES）与 GBA 等经典游戏模拟器，且能在不同硬件平台上运行。

开发调试的主要环境是 **Windows 应用环境**：内核与应用软件须能在普通 Windows 桌面程序（Win32 / Win64 应用）中直接编译、运行、调试，无需嵌入式硬件即可完成绝大部分内核与应用开发。

### 1.2 项目目标

1. 提供一个**可理解性强**的实时操作系统内核，核心调度与同步逻辑清晰、简洁、可读。
2. 至少支持 **固定优先级抢占式调度** 与 **周期调度** 两种调度策略，并允许**调度策略扩展**（新增策略不改动内核核心）。
3. 从机制上**解决优先级反转**问题。
4. 提供**可移植层（Port Layer）** 与 **硬件抽象层（HAL）/ 设备驱动框架**，使内核与应用软件可在多硬件平台之间迁移。
5. 提供 **Windows 应用环境移植**，支撑在 Windows 上开发、调试内核与应用软件。
6. 在 CatOS 之上运行 **FC 与 GBA 模拟器**，形成可玩的复古游戏平台 CatGamer。

### 1.3 项目范围

**范围内：**

- 实时内核：任务管理、调度、同步互斥、时间管理、内存管理。
- 可移植层与至少两个移植：Windows（开发调试用）与至少一个嵌入式/其他目标平台。
- 硬件抽象层与设备驱动框架：显示、输入、音频、存储、定时器、串口等设备抽象。
- 模拟器集成：FC、GBA 模拟器作为 CatOS 任务运行。
- Windows 应用环境下的构建、运行、调试与测试工具链。

**范围外（本项目不实现，作为后续扩展）：**

- 文件系统、网络协议栈、图形用户界面框架、TUI/CLI 子系统。
- 对称多处理（SMP）支持（首版仅单核）。
- 虚拟内存 / 内存保护（MMU）与进程级隔离（首版为单地址空间，线程/任务模型）。

### 1.4 阅读对象

内核开发人员、模拟器集成人员、平台移植人员、测试人员、项目评审人员。

## 2. 术语与缩写

| 术语 | 含义 |
| --- | --- |
| RTOS | 实时操作系统（Real-Time Operating System） |
| TCB | 任务控制块（Task Control Block），描述任务全部状态的数据结构 |
| 抢占 | 高优先级任务就绪后立即中断低优先级任务的执行 |
| 固定优先级 | 任务优先级在创建时确定，运行期不改变 |
| 周期调度 | 按固定周期周期性地释放/运行任务的调度方式 |
| 优先级反转 | 高优先级任务被低优先级任务间接阻塞的现象 |
| 优先级继承 | 通过让低优先级持锁任务临时提升优先级来化解优先级反转的协议 |
| 互斥量 | 带优先级继承的排他锁，用于临界区保护 |
| 信号量 | 计数型同步原语 |
| 消息队列 | 任务间传递消息的 FIFO 通道 |
| 事件标志 | 任务间同步的位掩码事件 |
| tick | 内核时钟节拍，调度与延时的时间基准 |
| ISR | 中断服务例程（Interrupt Service Routine） |
| Port Layer | 可移植层，屏蔽体系结构相关的上下文切换、中断、时钟、原子操作 |
| HAL | 硬件抽象层（Hardware Abstraction Layer） |
| BSP | 板级支持包（Board Support Package） |
| 空转任务 | 无任务就绪时运行的系统最低优先级任务 |
| 确定性 | 相同输入与状态条件下，行为与执行时间可预期、可重复 |
| 独立环境 | freestanding：C 语言的一种实现环境，只保证少数头文件可用，**不保证标准库函数存在**；内核以此为默认构建环境 |
| 宿主环境 | hosted：C 语言的常规实现环境（含完整标准库与 CRT 启动）；宿主的库与 API **只在移植层内部**使用（见 4.8 节 FR-LIB） |
| 运行库 / CRT | C 标准库（libc）及其运行时启动支持（如 `main` 之前的初始化与退出处理） |

## 3. 总体架构约束

### 3.1 分层结构

系统采用自上而下的分层结构，上层只能调用相邻下层接口：

```
┌──────────────────────────────────────────────────────┐
│ 应用层（CatGamer 应用逻辑 / 游戏入口 / 测试用例）        │
├──────────────────────────────────────────────────────┤
│ 模拟器层（FC 模拟器、GBA 模拟器，运行在模拟器任务中）      │
├──────────────────────────────────────────────────────┤
│ 内核服务层（同步/通信/时间/内存/软定时器/任务管理 API）    │
├──────────────────────────────────────────────────────┤
│ 内核核心层（调度器、就绪队列、状态机、优先级继承协议）      │
├──────────────────────────────────────────────────────┤
│ 可移植层 Port Layer（上下文切换/中断/tick/原子操作）       │
├──────────────────────────────────────────────────────┤
│ 硬件抽象层 HAL + 设备驱动框架（显示/输入/音频/定时器/…）  │
├──────────────────────────────────────────────────────┤
│ 硬件（Windows x86-64、目标嵌入式/单板机平台）            │
└──────────────────────────────────────────────────────┘
```

- **内核核心层与可移植层之间必须通过明确、稳定的接口隔离**；核心层不得出现任何体系结构相关代码。
- **设备驱动框架与 HAL 隔离**具体硬件，模拟器与应用只面向抽象设备接口编程。
- **运行库独立性与平台无关性**：内核核心层、HAL 与**应用层**均不依赖任何标准库（libc）与宿主 API，可在裸机目标上构建运行；**宿主库/API 的使用只允许出现在移植层内部**（详见 4.8 节 FR-LIB）。应用源码与平台解耦：同一份 `apps/` 源码须能换用不同平台移植（Windows、Linux、单片机）而不改代码。

### 3.2 可理解性原则（贯穿性约束）

本系统为教学与研究型系统，**可理解性**是最高优先级设计约束之一，具体体现为：

- 每个模块职责单一，模块间通过清晰的接口解耦。
- 命名规范统一、直观（如 `task_`、`mutex_`、`sched_` 前缀）。
- 关键算法（调度、优先级继承）在源码中配套中文/英文注释与状态说明。
- 内核核心代码不含平台相关分支，核心逻辑一份源码可在 Windows 与嵌入式目标上编译运行。
- 禁止为了性能使用难以理解的技巧；优先可读的简单实现，性能优化须以注释说明并保持可读。
- 提供内核设计文档：任务状态机、调度流程、锁协议时序图。
- **验收基准**：具备 C 语言基础与基本操作系统概念的开发人员，可在数小时内通读内核核心并描述其调度与互斥流程。

## 4. 功能需求

> 需求编号规则：`FR-模块-序号`。每条需求应可独立测试与验收。

### 4.1 任务管理（FR-TASK）

| 编号 | 需求描述 |
| --- | --- |
| FR-TASK-001 | 系统支持创建与删除任务；任务拥有独立的 TCB 与任务栈。 |
| FR-TASK-002 | 任务状态至少包括：就绪（Ready）、运行（Running）、阻塞（Blocked）、挂起（Suspended）、终止（Terminated）；任务状态转换规则明确并文档化。 |
| FR-TASK-003 | 任务创建时可配置：入口函数、栈大小、优先级、任务名、用户参数。 |
| FR-TASK-004 | 提供任务延时（睡眠指定 tick）、任务挂起与恢复、任务自删除等控制接口。 |
| FR-TASK-005 | 提供任务运行期自我标识（如 `task_self()`），支持调试与断言。 |
| FR-TASK-006 | 提供任务相关信息查询接口（状态、优先级、栈使用率、运行计数），供调试监视器使用。 |

### 4.2 调度策略（FR-SCHED）

**需求 FR-SCHED-001 —— 固定优先级抢占式调度**

- 每个任务在创建时确定固定优先级，运行期优先级只能由优先级继承机制临时提升。
- 调度规则：就绪集中优先级最高的任务运行；高优先级任务就绪时**立即抢占**正在运行的低优先级任务。
- 同优先级任务默认按 FIFO 顺序执行；可配置为同优先级时间片轮转（Round-Robin）以支持"多任务均分 CPU"场景。
- 调度点（发生调度的时机）包括：任务创建/删除、任务进入阻塞、任务解除阻塞、互斥量释放、tick 处理、ISR 返回时。

**需求 FR-SCHED-002 —— 周期调度**

- 支持注册**周期任务**：每个周期任务声明周期 `T`（tick 数）与可选的相位偏移 `φ`。
- 系统按周期精确地周期性唤醒/释放周期任务；周期任务的调度仍遵循优先级规则（即周期调度与固定优先级抢占共用就绪队列，周期只是"何时释放"的规则）。
- 提供周期任务的注册、注销、周期动态调整接口。
- 提供系统级配置：节拍粒度（tick 周期）默认 1 ms，可配置。

**需求 FR-SCHED-003 —— 调度策略扩展机制**

- 内核提供统一的**调度器抽象接口**（如一组 `sched_ops` 函数指针集：初始化、加入就绪、移除就绪、tick 驱动、选择下一个任务、抢占通知）。
- 固定优先级抢占与周期调度作为两个可选的、可插拔的策略实现；系统启动时选择启用哪一种（或组合）。
- **新增调度策略（如 EDF、纯时间片轮转、实时单调 RMS 等）只实现该接口并注册，不允许修改内核核心代码。**
- 调度策略扩展须提供对应的可测试性支撑（见 FR-TEST-003）。

**需求 FR-SCHED-004 —— 就绪队列**

- 就绪队列管理须保证时间复杂度可预期（建议按优先级位图或按优先级链表实现），不允许随任务数线性退化的最坏情况调度延迟。
- 就绪队列统计信息可查询（当前就绪任务数、最高优先级等）。

**需求 FR-SCHED-005 —— 空转任务**

- 无任务就绪时运行系统最低优先级的**空转任务**；空转任务可统计 CPU 空闲率，供监视器展示 CPU 占用。

### 4.3 优先级反转解决（FR-PRIO）

| 编号 | 需求描述 |
| --- | --- |
| FR-PRIO-001 | 系统提供**互斥量（Mutex）**，互斥量实现 **优先级继承协议（PIP）**：当高优先级任务因等待某互斥量而阻塞时，持有该互斥量的低优先级任务立即**继承**高优先级任务的优先级，直到释放互斥量后恢复原优先级。 |
| FR-PRIO-002 | 优先级继承须支持**链式/传递**继承：嵌套持有多个互斥量时，继承沿持有链正确传递（如多级阻塞场景）。 |
| FR-PRIO-003 | 优先级继承的"继承—恢复"过程必须**可跟踪可测试**：提供观测接口，使测试能验证任何时刻任务的有效优先级正确。 |
| FR-PRIO-004 | **系统全局限定**：在采用互斥量保护临界区的场景下，不得出现无界优先级反转（即任意优先级任务被低优先级任务无限期阻塞）。 |
| FR-PRIO-005 | （可选、可配置）提供 **优先级天花板协议（PCP / Highest-Locker）** 作为替代方案；启用后同样满足 FR-PRIO-004。 |
| FR-PRIO-006 | 自旋锁/原子临界区仅用于极短临界区（ISR 与内核内部），且不被任务长期持有，避免引入优先级反转。 |

> 说明：为满足"尽可能易理解"，默认方案采用**优先级继承协议**；PCP 作为可选扩展。

### 4.4 同步与通信（FR-SYNC）

| 编号 | 需求描述 |
| --- | --- |
| FR-SYNC-001 | 提供**互斥量**（含 FR-PRIO-001 的优先级继承），支持嵌套获取与超时等待。 |
| FR-SYNC-002 | 提供**二值信号量**与**计数信号量**，支持任务与 ISR 双向释放（ISR 只能释放、不能阻塞等待）。 |
| FR-SYNC-003 | 提供**消息队列**：定长消息、FIFO 顺序、可配置队列深度、支持超时收发；任务与 ISR 均支持发送。 |
| FR-SYNC-004 | 提供**事件标志**：按位同步，支持"全部置位 / 任一置位"等待模式，支持 ISR 置位。 |
| FR-SYNC-005 | 所有阻塞型同步原语均支持**超时**，超时后任务自动解除阻塞并返回错误码。 |
| FR-SYNC-006 | 所有同步原语提供统一的等待队列管理，阻塞/唤醒流程与调度器正确联动（满足 FR-SCHED-001 的调度点要求）。 |
| FR-SYNC-007 | ISR 与任务的交互必须安全：ISR 内禁止阻塞，所有 ISR 调用的内核服务具备明确的可调用性声明（文档化：哪些 API 可安全用于 ISR）。 |

### 4.5 时间管理（FR-TIME）

| 编号 | 需求描述 |
| --- | --- |
| FR-TIME-001 | 内核维护单调递增的**系统节拍计数**，可由移植层 tick 中断驱动。 |
| FR-TIME-002 | 提供 **tick 延时**（`sleep(tick)`）与基于系统时间查询接口（当前 tick 数、可换算为毫秒/秒）。 |
| FR-TIME-003 | 提供**软定时器**：一次性与周期性定时器、可动态创建/删除、超时回调在任务或 ISR 上下文中安全执行（执行上下文可配置并文档化）。 |
| FR-TIME-004 | 周期调度的周期与软定时器精度以 tick 为粒度；对超时唤醒的延迟误差（抖动）给出可测指标（见 NFR-003）。 |

### 4.6 内存管理（FR-MEM）

| 编号 | 需求描述 |
| --- | --- |
| FR-MEM-001 | 首版采用**静态内存池**策略：任务栈、TCB、队列缓冲区等在系统初始化时预分配，运行时分配确定性、无碎片。 |
| FR-MEM-002 | 提供基于**定长内存池**（或等价确定性机制）的动态分配接口，满足任务内部需要小量动态内存的场景；分配/释放时间可预期。 |
| FR-MEM-003 | 内核核心不使用标准库堆（malloc/free）以保证确定性与嵌入式可移植性；移植到 Windows 调试环境时可提供内存越界/泄漏检查支持（见 FR-WIN-005）。 |
| FR-MEM-004 | 提供内存使用统计接口（池用量、最大用量），供监视器展示。 |

### 4.7 可移植层（FR-PORT）

| 编号 | 需求描述 |
| --- | --- |
| FR-PORT-001 | 定义完整、最小化的**移植层接口**（唯一允许包含体系结构相关代码的层），包括但不限于：上下文切换、任务栈初始化、临界区进入/退出、原子操作、内存屏障、tick 时钟源、ISR 进入/退出包装。 |
| FR-PORT-002 | 提供**上下文切换**实现：保存/恢复任务 CPU 寄存器上下文；首次调度时正确启动新任务入口。 |
| FR-PORT-003 | 提供 **tick 时钟源**：周期性触发内核时钟（tick 周期可配置）。 |
| FR-PORT-004 | 提供 **ISR 包装**：中断进入保存上下文、通知内核、调用注册的 ISR、中断返回时判断是否需要切换任务。 |
| FR-PORT-005 | 提供原子操作（原子增减、置位/清除、交换）与临界区保护原语。 |
| FR-PORT-006 | **核心层零移植代码**：内核核心层源码中不得出现 `#ifdef` 平台分支或体系结构汇编；所有平台差异封装在移植层。 |
| FR-PORT-007 | 每个移植目标须附移植文档：如何为新平台实现该层、如何验证移植正确性。 |

### 4.8 运行库独立性与平台无关性（FR-LIB）

> 目标 1：内核（核心层 + 可移植层 + HAL）在**不依赖任何标准库（libc）** 的前提下可构建、可运行，从而能直接落到裸机/嵌入式目标。
> **独立环境（freestanding）** 是内核的默认构建方式。
> 目标 2：**应用层（CatGamer 应用、模拟器适配层、demo、测试）与平台无关**——同一份应用源码须能在不同平台移植（Windows、后续 Linux、各类单片机）下编译运行，切换平台不改动应用源码。
> 由此得到一条统一规则：**宿主操作系统/运行库（CRT、Win32、Linux libc、POSIX 等）的使用只允许出现在移植层 `kernel/port/<target>/` 内部**，内核核心层、HAL 与应用层一律不得直接使用宿主库或宿主 API；应用所需的输出、原子操作、时间、内存/字符串工具等，全部由公共 API 提供、由移植层实现。
>
> **自带运行库的形态**：CatOS 自有的 C 运行库放在独立目录 `lib/`，与 ISO C 头文件**一一对应**（`catos_string.h` ← `<string.h>`、`catos_stdio.h` ← `<stdio.h>`、`catos_stdlib.h` ← `<stdlib.h>`、`catos_ctype.h` ← `<ctype.h>`、`catos_assert.h` ← `<assert.h>`），函数一律 `catos_` 前缀。首版只实现重要功能，各头文件内以 `/* TODO(待扩充) */` 列出后续要补的函数，以便逐步向标准库方向扩充。层级为：`lib/`（运行库）→ `kernel/src`（核心）→ `kernel/port/<target>`（移植层）→ `apps/`。
>
> **换行约定**：应用输出**不做任何翻译**——格式串里的 `\n` 原样写出，要 CRLF 就自己写 `"\r\n"`；系统自身消息（panic、将来的内核日志）的换行由配置项 `CATOS_CFG_NL` 决定（`"\n"` 或 `"\r\n"`）。

| 编号 | 需求描述 |
| --- | --- |
| FR-LIB-001 | **内核零标准库依赖**：内核核心层与 HAL 的源码不得调用 C 标准库函数（`memcpy`/`printf`/`malloc`/`abort`/`exit` 等）；内核核心层与 HAL 的目标文件中不得存在**未定义的标准库符号**（通过符号表扫描验证，白名单仅为移植层接口、应用公共接口与编译器运行时内建）。移植层不受此限——它是唯一允许引用宿主库的一层（FR-LIB-006），其宿主依赖须在移植文档中列明（FR-PORT-007）。 |
| FR-LIB-002 | **头文件限定为独立环境头**：内核核心层、HAL 与**应用层**只允许包含 ISO C 规定的独立实现头（`stdint.h`、`stddef.h`、`stdbool.h`、`limits.h`、`float.h`、`stdarg.h`、`iso646.h`）与 CatOS 自有头（`"catos/…"`、`"catos_*.h"`）；禁止包含需要宿主运行时的头（`stdio.h`、`stdlib.h`、`string.h`、`time.h`、`errno.h`、`assert.h` 等）及宿主/平台专用头（`windows.h`、`unistd.h`、`pthread.h` 等）。**包含形式约定**：CatOS 自有头一律用 `#include "…"`，只有编译器/标准库头与移植层的宿主头可以用 `#include <…>`（由 FR-LIB-007 的检查脚本强制）。**例外**：编译器为目标平台自动生成的启动脚手架（如 32 位 MinGW 为应用 `main()` 生成的 `__main` 调用）不计入本约束——它不是源码级宿主调用。移植层与第三方代码的例外分别见 FR-LIB-006、FR-LIB-010。 |
| FR-LIB-003 | **自带运行支持（CatOS 运行库）**：CatOS 自带平台无关的 C 运行支持实现，放在 `lib/`，与 ISO 头文件一一对应并以 `catos_` 前缀命名（`catos_memcpy`/`catos_memset`/`catos_memmove`/`catos_memcmp`/`catos_strlen` 等，可选最小 `catos_vsnprintf`/`catos_snprintf`），经公共头开放给内核与**应用**使用，并可独立测试。该实现**同时以 ISO 同名符号导出**（`memcpy`/`memset`/`memmove`/`memcmp`/`strlen`），以满足编译器隐式生成的库调用（结构体赋值/清零等）——这类调用**不得在链接期落到 libc**。 |
| FR-LIB-004 | **禁止使用的运行时设施**：内核核心层与 HAL 不得使用动态内存分配（见 FR-MEM-003）、`exit`/`abort`/`atexit`、`setjmp`/`longjmp`、浮点运行库、线程局部存储与其他可重入机制；内核入口由移植层**显式调用**，不依赖宿主 CRT 的 `main` 之前初始化（区段构造/析构、`argc/argv` 与环境变量一律不使用）。**注**：应用层（`apps/`）不受"不得有 `main`"的约束——应用保留 `int main(void)` 作为入口函数（由宿主 CRT 启动），但其中不得出现宿主 API。移植层为承载宿主环境所需的脚手架（宿主线程创建、宿主内存分配、进程入口与退出等）不受此限，但须在移植文档中列明。 |
| FR-LIB-005 | **断言与致命错误自实现**：CatOS 自带断言与致命错误机制（`CATOS_ASSERT` / `catos_panic`，见 `catos_assert.h`），诊断文本由运行库格式化，输出与停机经移植层的 `catos_port_panic()` 完成；不得使用 libc 的 `assert`/`abort`。panic 通道不得加锁（出错时日志锁可能正被已挂起的任务持有）。 |
| FR-LIB-006 | **宿主库的使用范围仅限于移植层**：允许使用宿主操作系统库/API（CRT、Win32；后续 Linux 移植的 libc/POSIX；单片机移植的编译器运行时与寄存器访问）的代码**只能在 `kernel/port/<target>/` 内部**。任务线程创建/终止、调试输出后端、tick 时钟源、宿主定时器、以及应用的**进程结束**（`catos_exit` 的后端实现）等一切宿主相关实现均属移植层职责；内核核心层、HAL 与 `apps/`（应用、demo、测试）不得出现宿主头文件或宿主 API 调用（与 FR-PORT-006、FR-WIN-004 一致：核心源码在各平台逐字共享）。新增移植层不得要求改动应用源码。 |
| FR-LIB-007 | **构建与验证须强制**：内核与运行库在目标平台以独立环境选项构建（如 `-ffreestanding -fno-builtin`，嵌入式目标进一步以 `-nostdlib` 链接；`-fno-builtin` 同时防止编译器把运行库自己的字节循环识别成库调用而递归）；每个里程碑交付前执行运行库依赖检查——**内核核心层/HAL 对象文件与应用目标文件**的未定义符号扫描 + 头文件包含检查（FR-LIB-002），移植层对象文件的宿主符号单独列出并核对（FR-LIB-006）。**参考实现**：`tools/check_libc.sh <里程碑目录> <构建目录>`（另含可执行文件链接期符号检查与跨里程碑共享文件一致性检查）；检查结果记入该里程碑 `README.md` 的验证步骤（FR-DOC-002/004）。 |
| FR-LIB-008 | **应用层平台无关性**：`apps/` 下的演示、测试与 CatGamer 应用只依赖 CatOS 公共接口（内核服务 API、HAL 设备抽象、运行支持），**不得**包含宿主头文件、调用宿主 API、使用宿主线程/同步/IO 设施；同一份应用源码须能在多个移植（Windows 现在，Linux 与单片机后续）下编译运行，新增平台移植时应用源码零改动（构建系统按 `CATOS_TARGET`/平台选择移植层与 BSP，见 FR-PLAT-002）。 |
| FR-LIB-009 | **面向应用的公共运行支持设施**：为使应用平台无关，CatOS 向应用提供下列公共设施：①**日志/调试输出**（`catos_printf`／`catos_write(buf,len)`／`catos_putchar`：**格式化在运行库**、平台无关且输出完全一致，**宿主输出后端在移植层**（Windows → Win32 `WriteFile`、单片机 → 串口、Linux → `write`），一次调用即一段连续输出、不被其它任务交错；与 FR-WIN-005 的调试设施衔接）；②**原子操作**（`catos_atomic_*`，由移植层实现，应用不得使用宿主原子内建）；③时间与延时（FR-TIME）；④字符串/内存工具（FR-LIB-003 的 `catos_mem*`/`catos_str*`）；⑤**应用结束与结果上报**（`catos_exit(code)`：宿主目标上经移植层映射为进程退出码供 CI 判定，无进程概念的嵌入式目标上改为输出结果并停机/复位，见 FR-TEST-005）。 |
| FR-LIB-010 | **第三方代码的库依赖须经平台运行支持层**：应用层引入的第三方代码（如模拟器核心）若需要 libc/数学库函数（`malloc`、`printf`、`memcpy`、`sinf` 等），须由平台**运行支持层**提供同名实现或适配映射（分配→内存池 FR-MEM-002、输出→日志设备、数学→软浮点或编译器内建等），**不得直接链接宿主 libc、不得依赖宿主服务**；应用目标文件的未定义符号须全部由 CatOS 运行支持/移植层满足。模拟器核心的实际依赖清单与可行性在 M5 评审确认（见 A-10）。 |

> **说明**：本约束对新增与修改的代码**自 M2 起强制生效**。**M0/M1 已交付代码中的既存依赖已就地整改完毕**（两个里程碑均补齐了 `lib/` 运行库与移植层后端），整改内容：
>
> - **新增设施**：`lib/`（`catos_string.h`/`catos_stdio.h`/`catos_stdlib.h`/`catos_ctype.h`/`catos_assert.h` + `catos_backend.h`/`catos_libcfg.h`）、`catos/catos_atomic.h`（原子操作）、移植层 `kernel/port/win32/port_rt.c`（日志后端、panic、退出、原子操作实现）。
> - **内核侧（已改）**：`kernel/src/task.c`、`kernel/src/mutex.c` 原用 `string.h` 的 `memset` → 改用 `catos_memset`（运行库）。
> - **应用侧（已改）**：`apps/demo`、`apps/tests` 原用 `stdio.h` 的 `printf`、`stdlib.h` 的 `exit`、`string.h` 的 `memcmp`、`windows.h` 的 `InterlockedIncrement` → 分别改用 `catos_printf`/`catos_putchar`、`catos_exit`、`catos_memcmp`、`catos_atomic_inc`；`apps/tests/test_common.h` 不再包含任何宿主头。
> - **验证**：`tools/check_libc.sh m0_kernel_skeleton build/m0`、`tools/check_libc.sh m1_sched_core build/m1` 全项通过；实测数据见两个里程碑的 `README.md`。
>
> 唯一的行为差异：应用输出原经 CRT 文本模式把 `\n` 翻成 CRLF，现由运行库原样写出（LF）；这是"跨平台字节一致"的预期结果，已在各 README 与 `docs/design/kernel.md` 记录。

| 编号 | 需求描述 |
| --- | --- |
| FR-WIN-001 | 内核、可移植层、HAL、模拟器与 CatGamer 应用均可编译为 **Windows 桌面应用程序**（原生 Win32/Win64 可执行文件），无嵌入式硬件即可完整运行。 |
| FR-WIN-002 | Windows 移植采用线程/纤程（Fiber）映射任务，通过模拟 tick（定时器线程/高精度定时器）驱动调度，实现与嵌入式移植**行为等价**的抢占式调度。 |

### 4.13 里程碑文档要求（FR-DOC）

> 每个里程碑都是自包含文件夹，须随附该里程碑的独立文档，保证任何时刻可独立构建、运行与理解。

| 编号 | 需求描述 |
| --- | --- |
| FR-DOC-001 | **每里程碑一个独立文档**：每个里程碑文件夹内必须包含 `README.md`，随该里程碑源码一起交付与维护。 |
| FR-DOC-002 | 里程碑文档须至少包含：**交付内容**（实现的功能与覆盖的需求编号）、**目录结构**、**构建步骤**（工具链与完整命令）、**运行/验证步骤**（演示与测试命令、预期结果/实测结果）、**已知限制**、**下一步**。 |
| FR-DOC-003 | **文档随里程碑演进**：新里程碑从上一里程碑复制文件夹后，`README.md` 须同步更新到对应里程碑状态，不得与源码脱节；上一里程碑文档保持历史快照不变。 |
| FR-DOC-004 | **验收要求**：每个里程碑交付时，按其 `README.md` 的构建/运行步骤应能干净地完成构建与运行验证（评审时抽查）。 |

## 5. 非功能需求（NFR）

| 编号 | 类别 | 需求描述 |
| --- | --- | --- |
| NFR-001 | 可理解性 | 内核核心模块数量合理、单一职责；提供状态机、调度、锁协议的图表化文档；满足 3.2 节验收基准。 |
| NFR-002 | 可移植性 | 内核核心与体系结构无关（FR-PORT-006）；新增一个目标平台只需实现移植层 + BSP + 设备驱动，**不改动核心、HAL、应用与模拟器逻辑**（FR-LIB-006/008）；应用层与宿主平台解耦，换平台不改应用源码。 |
| NFR-003 | 实时性 | 初始参考指标（评审确认）：上下文切换开销、调度延迟、中断响应时间、超时唤醒抖动均给出可测目标；示例基线：Cortex-M 上调度延迟 ≤ 数 µs、tick 抖动 ≤ 1 tick。Windows 环境同样提供抖动测量工具。 |
| NFR-004 | 确定性 | 所有内核服务的最坏执行时间可预期，不依赖硬件加速或动态频率；内存分配无碎片。 |
| NFR-005 | 资源占用 | 内核静态 RAM 占用给出目标上限（如 ≤ 若干 KB，依平台在评审时确认）；任务栈、TCB 等资源量可配置。 |
| NFR-006 | 可扩展性 | 三处明确扩展点：调度策略（FR-SCHED-003）、设备驱动（FR-HAL-001）、目标平台（FR-PORT/FR-PLAT）。 |
| NFR-007 | 可靠性 | 系统 API 定义明确返回值与错误码；非法调用（如 ISR 内阻塞）有断言或文档化行为；初始化失败可诊断。 |
| NFR-008 | 可维护性 | 统一代码风格与命名规范；公共头文件为稳定接口并带注释；核心 API 有文档；保持向后兼容的接口变更管理。 |
| NFR-009 | 许可合规 | 采用的模拟器核心（如候选 FCEUX/Nestopia、mGBA 等）须为开源且许可允许二次分发与修改；在 README/文档中列明许可与归属。 |
| NFR-010 | 运行库独立性 | 内核核心层、HAL 与**应用层**均**不依赖任何标准库运行**（FR-LIB）：内核静态库与应用目标文件无未定义 libc 符号、仅包含独立环境头文件；可在无 libc 的裸机目标上独立启动；确定性与资源占用（NFR-004/005）不依赖宿主运行时；宿主库依赖仅存在于移植层。 |

## 6. 边界与排除项

首版**明确不实现**：

- 文件系统、网络协议栈、完整 GUI 框架。
- 多核/SMP 调度。
- 内存保护（MPU/MMU）、进程隔离、用户态/内核态分离。
- 电源管理、低功耗调度。
- 调试代理/主机端图形化调试器（可用日志与监视器替代）。

上述项作为后续版本候选扩展方向，设计时应预留接口空间但不在首版实现。

## 8. 验收标准（总纲）

- **AS-1 内核可运行**：在 Windows 应用环境构建并运行内核，演示任务创建、抢占、延时、同步原语工作正常（对应 FR-TASK / FR-SCHED / FR-SYNC / FR-TIME）。
- **AS-2 两种调度策略**：分别以固定优先级抢占与周期调度模式运行同一套演示程序，行为符合 FR-SCHED-001 / 002 描述。
- **AS-3 调度可扩展**：实现一个新增测试调度策略并注册，不改内核核心，功能与回归测试通过（FR-SCHED-003、FR-TEST-003）。
- **AS-4 优先级反转化解**：构造经典优先级反转场景，验证继承行为与"无界反转不发生"（FR-PRIO、FR-TEST-002）。
- **AS-5 双移植共享核心**：内核核心源码在 Windows 与嵌入式目标上编译运行，行为一致（FR-PORT、FR-WIN-004）。
- **AS-6 设备框架**：Windows 平台通过统一设备接口驱动显示/输入/音频设备，语义正确（FR-HAL）。
- **AS-7 模拟器运行**：在 Windows 平台启动 CatGamer，成功运行至少一款 FC 与一款 GBA 样例游戏，帧率与声音达标（FR-GAME、FR-TEST-004）。
- **AS-8 可理解性**：按 3.2 节基准由独立人员评审，核心调度与互斥逻辑可被通读理解；文档与源码齐全（NFR-001）。
- **AS-9 无标准库运行与应用层平台无关**：内核静态库与应用目标文件通过运行库依赖检查（未定义符号扫描 + 头文件包含检查，均无 libc 与宿主 API 依赖，宿主依赖只在移植层出现）；内核可在支持独立环境构建的目标上不依赖 libc 启动；同一份核心源码与**同一份应用源码**在至少两个移植（Windows 与 M6 的嵌入式目标）上构建运行，应用源码零改动（FR-LIB、NFR-002/010）。

## 9. 实施计划（概要里程碑）

| 阶段 | 内容 | 对应需求 |
| --- | --- | --- |
| M0 内核骨架 | 项目结构、构建系统、任务管理、就绪队列、空转任务、Windows 移植最小集 | FR-TASK、FR-PORT、FR-WIN |
| M1 调度核心 | 固定优先级抢占、调度抽象接口、优先级继承互斥量 | FR-SCHED-001/003、FR-PRIO |
| M2 同步与时间 | 信号量、消息队列、事件标志、tick、延时、软定时器；按需扩充 `lib/` 运行库（如 `catos_stdlib.h` 的内存池分配，接 FR-MEM-002） | FR-SYNC、FR-TIME、FR-LIB |
| M3 周期调度 | 周期任务框架、统计、调度测试 | FR-SCHED-002、FR-TEST |
| M4 HAL/设备 | 设备驱动框架、显示/输入/音频设备、Windows 后端 | FR-HAL |
| M5 模拟器集成 | FC/GBA 模拟器移植、适配层、CatGamer 应用框架；模拟器第三方依赖经平台运行支持层满足 | FR-GAME、FR-LIB |
| M6 第二平台 | 选定嵌入式/单板机平台移植、BSP、驱动、冒烟；以 freestanding/`-nostdlib` 构建验证无 libc 依赖 | FR-PLAT、FR-PORT、FR-LIB |
| M7 测试完善 | 单元/集成/性能测试、文档补全、验收 | FR-TEST、NFR、第 8 节 |

> **流程约定**：每个里程碑交付时，除实现对应需求外，还须随附该里程碑的独立文档（`README.md`），
> 内含构建与运行步骤（FR-DOC-001/002）。详见第 4.13 节。
>
> **运行库约束（FR-LIB）**：内核零标准库依赖与**应用层平台无关**是**跨里程碑的贯穿约束**，自 M2 起对新增/修改的代码强制生效；
> M0/M1 已交付代码中的既存依赖（内核的 `string.h`/`memset`；应用的 `printf`/`exit`/`windows.h`）**已就地整改完毕**（见 4.8 节说明）；
> 每个里程碑的 `README.md` 须记录运行库依赖检查结果（`tools/check_libc.sh`）。
